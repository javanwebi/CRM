# Security model

The trusted API authenticates database-backed sessions and derives user identity from the session, never from a user-submitted user_id. A tenant path is not authorization. Each business transaction sets app.user_id with transaction-local lifetime, changes role to crm_runtime, checks a permission in the database, then executes queries with explicit tenant filters. The runtime role is NOLOGIN and NOBYPASSRLS. RLS is forced on tenant business tables. Composite foreign keys prevent cross-company relationships.

`private.can` is a narrowly scoped SECURITY DEFINER lookup used to avoid recursive membership/role policies. It has an empty search_path, lives outside exposed schemas, rejects an absent identity and is executable only by crm_runtime. It trusts transaction-local identity supplied by the server. A party with the server database credential can impersonate users; this credential is a privileged trust boundary and must remain in the host's secret store. End users never receive SQL connectivity or these credentials.

Authentication/bootstrap/team code uses a dedicated crm_server login with explicit policies for the necessary identity, membership and configuration tables. This role is NOINHERIT and NOBYPASSRLS, has no direct access to customers/contacts/deals/tasks, and can SET ROLE crm_runtime for scoped business operations. A further hardening step can move bootstrap into narrowly granted server-only procedures. Do not give this credential to a worker. Worker jobs are not authorization, and all AI execution is disabled even if a supplied approval ID looks valid.

The custom users table stores scrypt password hashes, not Supabase Auth users. No password reset or email verification is currently implemented. In production use HTTPS, secure cookies and the exact APP_ORIGIN. Authentication is rate-limited. The in-memory rate limiter is for one API instance; move to a Redis shared store before multi-replica operation. One trusted proxy hop is assumed; adjust trust proxy for your infrastructure. CSRF is mitigated by SameSite=Lax plus strict Origin checking where supplied. Add CSRF tokens before supporting cross-site clients.

Audit entries are append-only to runtime users; writes are made in the same transaction as CRUD changes. The privileged server/database administrator can still administer audit data. There are no automatic destructive migrations, no delete API and no enabled sensitive AI tools.

The users table permits only the trusted server role. Public anonymous/authenticated clients have no access to password hashes. All public tables have RLS enabled and all anon/authenticated grants are revoked.
